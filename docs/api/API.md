# API кабинета NRW-Bot — руководство

Документ описывает HTTP API, который обслуживает **Telegram Mini App** (`/cabinet/*`), **веб-админку** (`/cabinet/admin/*`) и принимает **вебхуки платёжных провайдеров**. Всё работает в одном процессе с ботом (FastAPI, включается настройкой `CABINET_ENABLED=true`).

Состояние документа: соответствует коду на 2026-09-21 (коммит с планом аналитики `cedaa4c`). Запланированные изменения аналитики вынесены в раздел [«Что изменится»](#что-изменится-план-центра-аналитики).

## Быстрый старт

Хосты (по конфигурации репозитория): Mini App и админка ходят на домен кабинета (`cabinet.nocto.online`), платёжные провайдеры — на `admin.nocto.online`. Внутри контейнера сервис слушает порт `8080` (`CABINET_PORT`).

**1. Войти.** Mini App получает от Telegram строку `initData` и меняет её на токен:

```bash
curl -X POST https://<домен>/cabinet/auth/telegram \
  -H "Content-Type: application/json" \
  -d '{"init_data": "<строка initData из Telegram.WebApp.initData>"}'
```

```json
{ "access_token": "eyJhbGciOiJIUzI1NiIs..." }
```

**2. Вызывать API с токеном.**

```bash
curl https://<домен>/cabinet/dashboard -H "Authorization: Bearer <access_token>"
```

**3. Ошибки** приходят как `{"detail": "текст"}` с соответствующим HTTP-статусом (см. [«Общие правила»](#общие-правила)).

## Аутентификация и роли

**Вход:** `POST /cabinet/auth/telegram` ([описание](reference-cabinet.md#post-cabinet-auth-telegram)).

- Подпись `initData` проверяется по алгоритму Telegram Web Apps: `secret = HMAC_SHA256(key="WebAppData", msg=BOT_TOKEN)`, затем HMAC-SHA256 от отсортированной строки `key=value` (без поля `hash`). Поле `auth_date` не должно быть старше **24 часов**.
- Пользователь создаётся автоматически при первом входе. Язык интерфейса берётся из `language_code` Telegram (`ru` или `en`, по умолчанию `ru`).
- В ответ выдаётся **JWT** (HS256), срок жизни **12 часов**, в токене `sub` — внутренний id пользователя. **Refresh-токена нет**: по истечении нужно снова войти по свежему `initData`.
- Токен передаётся заголовком `Authorization: Bearer <token>`.

**Проверки на каждом запросе:** токен валиден и не истёк (иначе `401`), пользователь существует (`401`), пользователь **не заблокирован** (иначе `403`). Блокировка действует сразу, отзыв токена не нужен.

**Роли:**

| Роль | Доступ | Условие |
|---|---|---|
| Гость | `POST /cabinet/auth/telegram`, `/health`, вебхуки | — |
| Пользователь | `/cabinet/*` | валидный токен, не заблокирован |
| Администратор | `/cabinet/admin/*` | пользователь с флагом `is_admin` **и** его `telegram_id` входит в `ADMIN_TELEGRAM_IDS`. Иначе `403` «Требуются права администратора» |

Признак `is_admin` приходит в `GET /cabinet/dashboard` (для показа входа в админку). Сам по себе он права не даёт: сервер проверяет их заново на каждом админском запросе.

## Общие правила

### Формат ответов и ошибок

- Тело запроса и ответа — JSON (`Content-Type: application/json`).
- Ошибка бизнес-логики: `{"detail": "человекочитаемый текст"}` и статус:

| Код | Значение |
|---|---|
| 400 | Некорректный запрос по смыслу (неизвестный фильтр, недостаточно средств, неверный промокод и т. п.) |
| 401 | Нет токена, токен невалиден/истёк, пользователь не найден |
| 403 | Пользователь заблокирован или недостаточно прав |
| 404 | Объект не найден |
| 422 | Ошибка валидации параметров/тела (формат ниже) |
| 502 | Внешний сервис (Remnawave, Telegram, платёжный провайдер) не ответил или вернул ошибку |
| 503 | Функция отключена в текущем режиме (вебхуки вне `PAYMENTS_MODE=real`) |

- Ошибка валидации (`422`) — стандартный формат FastAPI:

```json
{ "detail": [ { "loc": ["body", "period_days"], "msg": "Field required", "type": "missing" } ] }
```

- Тексты в `detail` — русские, предназначены для показа пользователю. **Не разбирайте их программно**, ориентируйтесь на HTTP-статус.

### Деньги

- Все суммы — **целые числа в копейках** (поля `*_kopeks`).
- Исключения: `amount_rub` в `POST /cabinet/admin/users/{id}/balance` — рубли (число); `GET /cabinet/admin/net-profit` возвращает рубли (числа с плавающей точкой); у промокода типа `balance` поле `value` — копейки, типа `days` — дни.
- Цены тарифов в `GET /cabinet/tariffs` уже включают скидку пользователя.

### Даты и время

- Даты и время — ISO-8601, значения хранятся и передаются в **UTC**. В продакшене (PostgreSQL) строки приходят со смещением `+00:00`; в локальной разработке на SQLite — без смещения; во всех случаях считайте значение UTC.
- Дневные графики (`revenue-timeseries`, `revenue-composition`) и метрики «сегодня» сейчас считаются по границам суток: «сегодня» — по московской полуночи, графики по дням — по UTC (см. [«Что изменится»](#что-изменится-план-центра-аналитики)).

### Пагинация

- Списки в админке принимают `page` (с 1) и возвращают `{"items": [...], "total": N, "page": P, "total_pages": T}`. Размер страницы фиксирован — **20**.
- История транзакций пользователя (`GET /cabinet/transactions`) — страницы по **15**.

### Служебные заголовки

- `X-Request-ID` (необязательный, `A–Z a–z 0–9 . _ -`, до 64 символов) — идентификатор запроса для сквозной отладки. Если не передан или некорректен, сервер генерирует свой. Возвращается в заголовке ответа `X-Request-ID` и присутствует во всех строках лога этого запроса.
- CORS: разрешённые источники задаются настройкой `CABINET_ALLOWED_ORIGINS` (список через запятую); методы и заголовки разрешены любые. Пустой список — CORS выключен.

### Лимиты

Ограничений частоты запросов на уровне приложения нет (при необходимости они настраиваются на реверс-прокси).

## Вебхуки платёжных провайдеров

Вебхуки вызывают платёжные провайдеры на домене `admin.nocto.online`. Они **работают только при `PAYMENTS_MODE=real`**: в режиме `stub` любой вебхук отвечает `503 {"status":"error","reason":"webhooks_disabled"}` (иначе заглушка позволила бы подтверждать платежи без оплаты).

**Общая логика.** Статус, пришедший в теле вебхука, — лишь повод проверить платёж: перед выдачей подписки сервер запрашивает статус (и сумму) у самого провайдера. Если провайдер недоступен, вебхук отвечает `400` — провайдер повторит колбэк, а фоновая задача-страховка подтвердит платёж в любом случае. Обработка идемпотентна: повторный вебхук по уже обработанному платежу ничего не выдаёт повторно.

Формат ответа — `{"status": "ok"}` при успехе и `{"status": "error", "reason": "<код>"}` при ошибке. Коды `reason`:

| `reason` | HTTP | Значение |
|---|---|---|
| `unauthorized` | 401 | Не прошла проверка подлинности |
| `invalid_json` | 400 | Тело не JSON |
| `no_transaction_id` | 400 | В теле нет идентификатора транзакции |
| `payment_not_found` | 400 | Платёж с таким id у нас не найден (провайдер должен повторить позже) |
| `verification_failed` | 400 | Не удалось подтвердить статус у провайдера |
| `processing_failed` | 400 | Внутренняя ошибка при обработке |
| `no_subscription_id`, `subscription_not_found` | 400 | Только Platega, события автоплатежей |
| `webhooks_disabled` | 503 | Режим не `real` |

### cisPay — `POST /cispay-webhook`

- Подпись: заголовок `X-Signature` = hex от HMAC-SHA256, где ключ — API-ключ магазина (`CISPAY_API_KEY`), а данные — **сырое тело запроса** (побайтово). Без ключа в настройках или без подписи запрос отклоняется (`401`).
- Используются поля тела: `id` (идентификатор платежа), `status`. Статусы: `PAID` — оплачен; `FAILED`, `EXPIRED`, `REFUNDED` — неуспешен (для ещё не оплаченных платежей); остальные — ожидание. Суммы `charged_amount`/`merchant_revenue` и время `paid_at` сейчас сохраняются только в сыром ответе платежа (`provider_raw_response`) и в выручке не используются; в плане аналитики они переносятся в отдельные колонки.
- Успех: платёж завершается, выдаётся подписка/подарок, начисляется реферальная комиссия.

### Platega — `GET|POST /platega-webhook`

- `GET` всегда `200 {"status":"ok","service":"platega_webhook"}` — Platega проверяет адрес при сохранении вебхука.
- `POST` без заголовков авторизации и с пустым телом — «пинг» проверки адреса, ответ `200`.
- Подлинность: заголовки `X-MerchantId` и `X-Secret` должны совпадать с настройками (`PLATEGA_MERCHANT_ID`, `PLATEGA_SECRET_KEY`); пустые настройки запрос не пропускают.
- Разовые платежи: поле `id` (или `transactionId`) и `status`: `CONFIRMED` — успех; `FAILED`, `CANCELED`, `EXPIRED` — неуспех; остальные — ожидание.
- События автоплатежей (Platega-подписки) распознаются по `paymentMethod=6`, наличию `SubscriptionId` или статусу с префиксом `SUBSCRIPTION_`. Статус подписки `SUBSCRIPTION_ACTIVATED` присылает пользователю уведомление об активации автоплатежа; `SUBSCRIPTION_CANCELLED`, `SUBSCRIPTION_FAILED`, `SUBSCRIPTION_PAST_DUE` выключают автоплатёж и уведомляют пользователя. Успешное списание (`CONFIRMED`) продлевает подписку на 30 дней; повторный колбэк по тому же списанию игнорируется.

### `GET /health`

Всегда `{"status":"ok"}`. База данных и внешние сервисы не проверяются — это проверка «процесс жив».

## Известные особенности и ограничения

- **Нет ограничения частоты, нет версионирования API, нет refresh-токена.** Токен нельзя отозвать до истечения, но блокировка пользователя проверяется на каждом запросе.
- **`/openapi.json` на момент написания доступен публично без авторизации** (отключён только Swagger UI). В плане центра аналитики схема закрывается, а источником истины становится файл `openapi.json` в этой папке.
- **MRR/ARR — прокси**, а не настоящий рекуррентный биллинг: MRR = выручка за последние 30 дней, ARR = MRR × 12. В интерфейсе это должно быть подписано.
- **Выручка сейчас брутто** (`Payment.amount_kopeks`) и привязана к времени создания платежа; после внедрения плана аналитики станет чистой суммой по времени оплаты.
- В `schemas.md` две схемы называются `PaginatedTransactionsResponse` (пользовательская и админская) — в OpenAPI они получают длинные имена вида `app__cabinet__…__PaginatedTransactionsResponse`.
- Тексты ошибок — на русском и могут меняться; не используйте их как коды.
- Отдельного аудит-журнала действий администратора нет: изменение баланса оставляет транзакцию пользователя, остальные операции (продление подписки, блокировка, сообщения) следа в БД не оставляют.

## Шаблоны автоматических сообщений

Бот сам отправляет 15 видов сообщений (оплата, истечение подписки, бонусы, автоплатёж, напоминания). Их тексты можно менять из админки — эндпоинты `/cabinet/admin/notifications/*` ([справочник](reference-admin.md#уведомления-бота)) — и из бота (`/admin` → «✉️ Сообщения»).

- Заводские тексты лежат в коде и всегда доступны; правки хранятся в БД и действуют **сразу** (кэш до 60 секунд, сбрасывается при сохранении).
- Текст — HTML Telegram; разрешены теги `b, strong, i, em, u, ins, s, strike, del, a, code, pre, tg-spoiler, blockquote, tg-emoji`. Подстановки `{имя}` — только из списка переменных события; значения экранируются.
- Кастомные эмодзи — `<tg-emoji emoji-id="…">символ</tg-emoji>` (символ обязан совпадать с «родным» символом эмодзи). Работают только если у владельца бота Telegram Premium; список известных ID — `GET /emoji`. В подписи кнопки эмодзи-кастомы запрещены.
- Событие можно выключить (`enabled: false`): сообщение не отправляется.
- Если Telegram отклонил сообщение из-за разметки или эмодзи, пользователь получает **заводской текст**, а в логе появляется `template_fallback`.

## Рассылки по пользователям

`POST /cabinet/admin/broadcasts/` создаёт рассылку и сразу отвечает `202` — отправка идёт
фоновой задачей. Прогресс — `GET /cabinet/admin/broadcasts/{id}` (опрос; `status`:
`in_progress` → `completed`/`partial`/`cancelled`/`interrupted`). Не более одной рассылки
одновременно (`409`, если уже есть `in_progress`). `POST .../{id}/cancel` останавливает
рассылку перед следующей пачкой получателей — уже отправленные сообщения не откатываются.

Медиа — только `file_id`, уже известный откуда-то ещё (загрузка файла через API не
поддерживается в этой версии). Категории аудиторий и кнопки-конструктор — `GET
/cabinet/admin/broadcasts/options`.

Подробности дизайна — `docs/superpowers/specs/2026-09-22-broadcast-api-design.md`.

## Что изменится (план центра аналитики)

Утверждённый дизайн и план реализации:
- Спецификация: [`docs/superpowers/specs/2026-09-21-analytics-center-design.md`](../superpowers/specs/2026-09-21-analytics-center-design.md)
- План (фундамент): [`docs/superpowers/plans/2026-09-21-analytics-foundation.md`](../superpowers/plans/2026-09-21-analytics-foundation.md)

Для потребителей API главное:

- Выручка станет **чистой** (после комиссии cisPay), по **времени оплаты**, без возвратов; цифры снизятся примерно на комиссию (~4%) и сдвинутся по границам суток.
- Все аналитические эндпоинты получат необязательный параметр `?tz=<IANA-имя>` (по умолчанию `Europe/Moscow`); в ответах появится поле `timezone` (у списков — заголовок `X-Report-Timezone`).
- `GET /cabinet/admin/revenue-timeseries?days=N` начнёт возвращать **ровно N точек** (сейчас N+1).
- В `recent-payments` поле `created_at` станет временем оплаты.
- В `overview` появятся поля `revenue_30d_gross_kopeks`, `fees_30d_kopeks`, `net_known_share_30d`, `timezone`.
- Новые эндпоинты: сверка с cisPay `GET /cabinet/admin/analytics/reconcile/cispay` и `POST …/reconcile/cispay/refunds`.
- Публичный `/openapi.json` будет закрыт.

После внедрения этот документ и справочники будут перегенерированы.

## Как обновлять документацию

```bash
# из корня репозитория; BOT_TOKEN — любая непустая строка
BOT_TOKEN=x python scripts/generate_api_docs.py
```

Скрипт пересоздаёт `reference-*.md`, `schemas.md` и `openapi.json` из кода: технические таблицы — из OpenAPI-схемы приложения, ошибки — разбором HTTPException в роутах, описания — из словаря `S` в самом скрипте. При добавлении эндпоинта скрипт напечатает, каких описаний или групп не хватает (`missing from groups`, `summaries missing`) — добавьте их в скрипт. `API.md` правится вручную.
