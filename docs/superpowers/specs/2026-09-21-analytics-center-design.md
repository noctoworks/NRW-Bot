# Центр аналитики админки — дизайн

Дата: 2026-09-21 · Статус: черновик на ревью · Репозиторий: NRW-Bot (бэкенд). Интерфейс — отдельный репозиторий NRW-MiniApp, после завершения его редизайна на shadcn/ui.

## 1. Контекст и проблема

Админка уже содержит аналитику (`app/services/analytics_service.py`, `app/cabinet/admin_routes.py`): обзор, график выручки, разбивки, LTV, когорты по выручке, реферальная воронка, чистая прибыль. Во фронтенде она сгруппирована во вкладки «Динамика / Продажи / LTV и когорты / Рефералы».

Три проблемы мешают принимать по ней решения (приоритеты владельца: **рост и деньги, удержание, маркетинг и промо**):

1. **Деньги не сходятся с кабинетом cisPay.**
   - Выручка считается по `Payment.amount_kopeks` (брутто) и по времени **создания** платежа (`Transaction.created_at`), а кабинет cisPay показывает `merchant_revenue` (нетто) по времени **оплаты** (`paid_at`).
   - Колонки `charged_amount_kopeks` и `merchant_revenue_kopeks` есть в БД (миграция `caa7bbb89896`), но не описаны в модели и не используются.
   - Возвраты (`REFUNDED` у cisPay) нигде не учитываются.
2. **Нет единого правила времени.**
   - «Сегодня» считается по московской полуночи (`time_utils.business_day_start_utc`), а график по дням, дням недели и «этот месяц» — по UTC.
   - Итог: последняя точка графика не равна карточке «выручка сегодня».
   - Кабинет cisPay режет сутки по времени браузера (часовой пояс зрителя).
3. **Нет истории событий.** `Subscription` — одна строка на пользователя. Для синхронных платежей `Payment.raw_payload` пуст (период продления не записан). Churn сейчас — снимок «сколько сейчас `expired`». Поэтому воронку, честное удержание, движение MRR и аттрибуцию промокодов, кампаний и скидок точно посчитать нельзя.

## 2. Цели и не-цели

**Цели**
- Денежные метрики сходятся с кабинетом cisPay (нетто, по `paid_at`, с возвратами, в выбранном часовом поясе).
- Единое правило времени во всей аналитике.
- Журнал событий как источник точных метрик роста, удержания и маркетинга.
- Новые аналитические API: рост и деньги, удержание, маркетинг, сверка с cisPay.

**Не-цели (v1)**
- Интерфейс (делается позже во фронтенде, после редизайна; новые вкладки «Воронка / Удержание / Маркетинг» и «Сверка» в разделе «Аналитика»).
- Рекламные расходы по кампаниям (нужно поле для ручного ввода), аналитика трафика, причины оттока (не собираются).
- Ежедневные снимки метрик (подход C) и кэширование ответов: добавляются, только если запросы станут медленными.
- Частичные возвраты (cisPay отдаёт только статус `REFUNDED`; возврат считается полным).

## 3. Принятые решения

| Вопрос | Решение |
|---|---|
| Источник точных метрик | Append-only журнал событий `analytics_events` (подход B), а не расчёт «на лету» и не снимки. |
| Хранение и передача времени | Всегда UTC. |
| Границы дня/недели/месяца | Один отчётный пояс: `REPORT_TIMEZONE` (по умолчанию `Europe/Moscow`) плюс необязательный `?tz=` на каждом эндпоинте (IANA-имя, проверяется по `zoneinfo`). Фронтенд сможет подставлять пояс браузера, повторяя поведение cisPay. |
| Что считается выручкой | Чистая сумма мерчанту: `COALESCE(merchant_revenue_kopeks, amount_kopeks)`. Рядом всегда отдаются оборот (`charged`, брутто) и комиссия (разница). |
| К какому времени привязана выручка | `paid_at` (время успешной оплаты). |
| Возвраты | Платёж со статусом `refunded` не входит в выручку. |

## 4. Архитектура

```
Денежные пути ──record_event()──▶ analytics_events ─┐
(покупка, финализация,                              ├─▶ analytics/*  ──▶ /cabinet/admin/analytics/*
 вебхуки, промо, реферал,   Payment (+paid_at,      │    (SQL-агрегации)     (require_admin, read-only)
 регистрация, триал)          net, refunded) ──revenue_expr()
                                                    │
cisPay /transactions ──reconcile job/endpoint───────┘
```

Новые и изменяемые модули:
- `app/services/time_utils.py` — единственный источник границ времени: `to_report_tz`, `day_start_utc`, `week_start_utc`, `month_start_utc`, `window(days, tz)`; все принимают пояс параметром. Старый `business_day_start_utc` остаётся обёрткой над новым API (используется в `handlers/admin.py`).
- `app/services/revenue.py` — `revenue_expr()` и `revenue_query()`: единственное место, где определено, что такое выручка (чистая, по `paid_at`, без возвратов, без оплат с баланса, типы `subscription_payment` и `gift`). `analytics_service` и новые метрики используют только его.
- `app/services/analytics_events.py` — `record_event(db, type, ...)`.
- `app/services/analytics/` — пакет метрик (`growth.py`, `retention.py`, `marketing.py`, `reconcile.py`), тонкие роуты в `app/cabinet/analytics_routes.py`.
- `scripts/backfill_analytics_events.py` — разовое восстановление истории.

## 5. Модель данных

**`analytics_events`** (только добавление):

| Поле | Тип | Смысл |
|---|---|---|
| `id` | int PK | |
| `occurred_at` | timestamptz, индекс | момент события, UTC |
| `type` | str(32) | см. ниже |
| `user_id` | FK `users.id`, `ON DELETE SET NULL`, индекс | удаление пользователя не искажает агрегаты |
| `tariff_id` | FK, nullable | |
| `days` | int, nullable | выданный срок |
| `amount_kopeks` | bigint, nullable | чистая сумма мерчанту (как выручка) |
| `campaign_id`, `promo_code_id`, `payment_id` | nullable | привязки для аттрибуции |
| `discount_percent`, `discount_kind` | nullable | `group` / `sale` / `winback` |
| `source` | str(16) | `live` или `backfill` |
| `dedupe_key` | str(128), **unique** | идемпотентность |

Индексы: `(type, occurred_at)`, `(user_id)`, `unique(dedupe_key)`.

**`payments`** (миграция, только добавление):
- `paid_at` timestamptz nullable (индекс). У cisPay берётся из ответа `paid_at`, у остальных — момент финализации. Backfill: из `provider_raw_response`, иначе время создания транзакции.
- Модель дополняется уже существующими в БД колонками `charged_amount_kopeks` и `merchant_revenue_kopeks`. Заодно в модель `PromoGroup` добавляется `is_active` (есть миграция `13a3c1d46134`, нет поля).
- Новый статус `refunded` (значения: `pending|success|failed|refunded`) и `refunded_at` nullable.

**Типы событий v1:** `user_registered`, `trial_started`, `subscription_first_paid`, `subscription_renewed`, `subscription_expired`, `promocode_activated`, `gift_redeemed`, `referral_reward_paid`, `bonus_granted` (дни или баланс за кампанию, приглашение, промокод — «стоимость» маркетинга), `payment_refunded`.

**Ключи идемпотентности:** `user:{id}:registered`, `user:{id}:trial`, `payment:{id}:paid` (тип `first_paid` или `renewed` определяется при записи по наличию более раннего платного события пользователя), `payment:{id}:refunded`, `sub:{id}:expired:{end_date}`, `promo:{code_id}:{user_id}`, `gift:{id}:redeemed`, `referral_earning:{id}`, `bonus:{kind}:{ref}`.

**Точки записи:** `provision_or_extend_subscription`; `finalize_pending_payment`; `purchase_or_renew_subscription`; автоплатёж-вебхук; `activate_promocode`; `redeem_gift_code`; регистрация и триал в `handlers/start.py`; `apply_campaign_bonus`; `credit_referral_earning` и `credit_referral_invite_bonus`; `expiry_checker`; сверка (возвраты).

**`record_event`:** вставка идёт в **той же транзакции**, что и денежная операция, через `INSERT … ON CONFLICT DO NOTHING` по `dedupe_key` (диалектные `insert` для Postgres и SQLite). Повтор не создаёт дубль, а сбой записи не «отравляет» сессию, как обычный `IntegrityError`. Событие никогда не пишется отдельной транзакцией: не бывает события без платежа и платежа без события.

## 6. Время

- `REPORT_TIMEZONE` в настройках (`Europe/Moscow` по умолчанию), зависимость `tzdata` (в `python:slim` и на Windows иначе пояс не находится).
- Окна «за N дней» выравниваются по границам отчётных дней: сумма графика за период равна карточке за то же окно.
- Ответы API: дни — строки `YYYY-MM-DD` в отчётном поясе; моменты времени — ISO-8601 в UTC; в каждом ответе поле `timezone`.
- Существующие метрики (обзор, график, дни недели, «этот месяц», пульс подписок) переводятся на `time_utils` и `revenue.py`.

## 7. Выручка

`revenue_expr` = чистая сумма платежей `status='success'`, `provider != 'balance'`, привязанных к транзакциям типов `subscription_payment` и `gift`, по времени `COALESCE(paid_at, transaction.created_at)`. У платежей без `merchant_revenue_kopeks` (старые Platega, Stars, TON) берётся `amount_kopeks`; в ответах есть доля `net_known`, показывающая, насколько выручка точна. Оборот (`charged`) и комиссия (`charged - net`) отдаются отдельными полями.

**Последствие:** все существующие цифры выручки, MRR, ARPU, LTV, когорт и чистой прибыли сместятся вниз примерно на размер комиссии (порядка 4% по данным cisPay) и на 3 часа по границам суток. Это осознанная коррекция, отражается в описании изменения.

## 8. API (`/cabinet/admin/analytics/*`)

Общие параметры: `from`/`to` (или `days`, максимум 731), `tz`. Общие поля ответа: `timezone`, `data_quality` = `{exact_since, backfill_share}`. Доступ — `require_admin`, только чтение.

**Рост и деньги**
- `funnel` — регистрация → триал → первая оплата → повторная, по когорте зарегистрированных в окне, конверсия между шагами, разрез по кампании.
- `mrr-movement` — по месяцам: новая выручка, продления, возвращённые, потерянные, чистый прирост; нормализация на 30 дней по `days` событий.
- `period-comparison` — текущий период против предыдущего такой же длины по границам отчётных дней.
- `forecast` — оценка выручки на 30 дней: плановые продления по `end_date` × историческая доля продлений по тарифу + средний темп новых продаж; вилка «от и до», помечено как оценка.
- `reconcile/cispay?date=` — сверка дня с cisPay (см. ниже).

**Удержание**
- `retention` — матрица когорт (неделя или месяц): доля оплатившая повторно на N-й период и доля с действующей подпиской.
- `trial-conversion` — доля триалов, ставших платными за 7/14/30 дней, медианное время до оплаты, по тарифам и кампаниям.
- `churn` — отток по периоду в разрезе тарифов и стажа.
- `at-risk` — списки с пагинацией: истекает за 7 дней и ни разу не продлевал; истекла 1–14 дней назад; подписка активна, но нет активности N дней.

**Маркетинг и промо**
- `campaigns` — регистрации, конверсия в оплату, чистая выручка, средний LTV, стоимость бонусов, ROI по бонусам.
- `promocodes` — активации, доля перешедших в платящих, выручка после активации, стоимость бонусов.
- `referrals-roi` — приглашённые, платящие, выручка от них, выплаченные комиссии, остаток после них.
- `discounts` — по видам скидок: заказы, выручка, «отданная» скидка, сравнение с равным окном без акции.

**Сверка с cisPay.** Тянет `GET /transactions` cisPay (`limit=100`, пагинация по `offset`), сравнивает с нашими платежами по `external_id` и по сумме дня в выбранном поясе. Отдельно выводит: платёж есть только у одной стороны, расхождение суммы, возвраты (`REFUNDED`). Обнаруженный возврат переводит платёж в `refunded`, пишет `payment_refunded` и убирает платёж из выручки. Запускается по запросу и фоновой задачей раз в сутки.

## 9. Тестирование

Тесты пишутся раньше кода; каждая проверка чувствительности — как в существующих тестах: временная поломка формулы должна ронять тест.

- **Время:** граница дня в 23:55 и 00:05 по МСК; разные пояса; невалидный `tz`; окно совпадает с карточкой.
- **Выручка:** нетто и запасной вариант с брутто; атрибуция по `paid_at`; возвраты; `net_known`.
- **События:** ровно одно событие на платёж при повторных вебхуках и повторных вызовах; сбой записи не ломает платёж; тип `first_paid` или `renewed` определяется корректно.
- **Backfill:** идемпотентность, метка `source='backfill'`.
- **Сверка:** моки ответов cisPay — платёж только у одной стороны, расхождение суммы, возврат.
- **Метрики:** на заранее построенном потоке событий с известным ответом.
- Ограничение: ветка Postgres для `ON CONFLICT` без CI проверяется только на SQLite и компиляцией SQL; закрывается при появлении CI.

## 10. Ошибки и защита

Невалидный `tz` даёт 422. Диапазон ограничен 731 днём. Пустые данные дают нули, а не ошибки. Окно раньше `exact_since` возвращает предупреждение в `data_quality`. Запись события всегда «тихая» (`ON CONFLICT DO NOTHING`), в транзакции денег исключений нет. Аналитические эндпоинты только читают.

## 11. Выкладка

1. Миграции (только добавляющие: новая таблица и nullable-колонки) — откат безопасен.
2. Деплой бэкенда.
3. `backfill_analytics_events.py` в режиме dry-run, затем боевой.
4. Сверка за прошлый день с кабинетом cisPay у владельца в его поясе.
5. Объявление о сдвиге цифр выручки на размер комиссии и границы суток.

Каждый подпроект получает свой план реализации.

1. **Фундамент:** `time_utils`, `revenue.py`, миграции и правка расхождения моделей, `analytics_events`, `record_event` и хуки, backfill, сверка и возвраты; перевод существующих метрик на единый расчёт выручки.

4. API «Маркетинг».
5. (Отдельно, в NRW-MiniApp, после редизайна) интерфейс: вкладки «Воронка / Удержание / Маркетинг» и «Сверка».

## 13. Риски и допущения

- Backfill определяет «первая оплата или продление» по порядку платежей пользователя — это приближение; хвост истории помечен `source='backfill'`, `data_quality` показывает `exact_since`.
- Обнаружение возвратов зависит от опроса `/transactions` cisPay; лимиты их API неизвестны, поэтому опрос редкий (раз в сутки и по запросу).
- Пояс кабинета cisPay — «по времени браузера» (со слов владельца). Проверяется сверкой за конкретный день; при расхождении достаточно поменять `REPORT_TIMEZONE` или передать `tz`.
- Данные до появления `paid_at` восстановлены приближённо (см. backfill).
