# API рассылок для веб-админки — дизайн

**Дата:** 2026-09-22
**Статус:** утверждён, готов к планированию реализации

## Проблема

Рассылки по пользователям существуют только в боте (`/admin` → «📢 Рассылка»,
`app/handlers/admin.py`): выбор аудитории → текст → медиа → кнопки →
подтверждение → отправка пачками с ретраями и историей в таблице
`broadcast_history`. Веб-админка ссылается на эндпоинты
`/cabinet/admin/broadcast/*`, которых нет — страница «Рассылки» получает 404.

Нужно дать веб-админке те же возможности через API, не дублируя логику
отправки (аудитория, батчи, флуд-контроль, кнопки-конструктор) отдельно от
бота.

## Архитектура

Общий сервис `app/services/broadcast_service.py` — единственное место, где
живёт логика отправки (аудитория, кнопки, батчи по 25 с паузой 1с, ретраи на
`TelegramRetryAfter`, обработка `TelegramForbiddenError`). И бот
(`app/handlers/admin.py`), и API (`app/cabinet/broadcast_routes.py`) вызывают
этот сервис — один код, одна таблица истории.

Константы и справочные функции переезжают из `admin.py` в сервис:
`BROADCAST_TARGETS`, `BROADCAST_BUTTONS`, `BROADCAST_BUTTON_ROWS`,
`DEFAULT_BROADCAST_BUTTONS`, `target_users()`, `target_display_name()`,
`result_keyboard()`. `admin.py` их импортирует — никакого дублирования
словарей категорий/кнопок.

### Модель запуска

- **Не мгновенная операция.** `POST` создаёт запись `BroadcastHistory` со
  статусом `in_progress`, запускает отправку фоновой `asyncio`-задачей и сразу
  отвечает `202` с `id` и `total_count`. Прогресс — через `GET .../{id}`
  (опрос).
- **Одна рассылка одновременно.** Если уже есть запись `in_progress` —
  `POST` отвечает `409`. Общий лимит Telegram (~30 msg/sec) один на процесс;
  две параллельные рассылки конкурировали бы за него без общей синхронизации
  флуд-контроля. Ограничение действует и для бота, и для API — они делят одну
  проверку через сервис.
- **Прогресс пишется в БД, не только в конце.** Сейчас бот коммитит
  `sent_count`/`failed_count`/`blocked_count` только после всей рассылки.
  Сервис будет коммитить их каждые ~5 сек в процессе (та же частота, с которой
  сейчас бот правит сообщение с прогресс-баром) — короткой отдельной сессией
  (`AsyncSessionLocal`), потому что фоновая задача переживает исходный
  HTTP-запрос и не может использовать его сессию.
- **Отмена.** `POST .../{id}/cancel` выставляет `asyncio.Event` в памяти
  сервиса (реестр `dict[int, asyncio.Event]` по id рассылки — тот же паттерн,
  что кэш правок в `message_templates/service.py`). Флаг проверяется перед
  каждой пачкой; уже отправленные сообщения не откатываются. Статус →
  `cancelled`.
- **Перезапуск процесса посреди рассылки.** Ничего не восстанавливается. При
  старте процесса (в `main.py`, до `supervise()`) один `UPDATE` помечает все
  записи со статусом `in_progress` как `interrupted` — иначе такая запись
  навсегда блокировала бы правило «одна рассылка одновременно» через 409.
- **Медиа.** Только `file_id`, полученный где-то ещё (например, админ
  переслал файл боту). Загрузка файла через API — не в этой версии.

### `BroadcastHistory.status`

Новые значения `cancelled` и `interrupted` (поле `String(20)`, миграция схемы
не нужна). Итоговый набор: `in_progress`, `completed`, `partial`, `cancelled`,
`interrupted`.

## API — `/cabinet/admin/broadcasts/*`

Тот же `require_admin`, что у остальной админки.

- **`GET /options`** → `{targets: [{key, label, recipient_count}], tariffs:
  [{id, name, recipient_count}], buttons: [{key, label}]}` — всё для формы
  одним запросом; счётчики через `target_users()`.
- **`POST /preview`** `{target: str}` → `{target_display_name, recipient_count}`.
- **`POST /`** `{target, text, media_type?, media_file_id?, buttons: list[str]}`
  → `202 {id, status: "in_progress", total_count}`. `409`, если уже есть
  рассылка `in_progress`. Валидация: `text` непустой и ≤4000 символов (как в
  боте), `media_type` из `{photo, video, document}` при указанном
  `media_file_id`, ключи `buttons` — подмножество известных.
- **`GET /`** — история, пагинация как в остальной админке (`page`, `page_size`,
  `total`).
- **`GET /{id}`** → `{id, status, target_type, target_display_name, total_count,
  sent_count, failed_count, blocked_count, created_at, completed_at}` — для
  опроса прогресса. `404`, если не найдена.
- **`POST /{id}/cancel`** → `202`. `404`, если не найдена; `409`, если уже не
  `in_progress`.

## Рефакторинг бота

`app/handlers/admin.py` не меняет UX (тот же FSM: аудитория → текст → медиа →
кнопки → подтверждение), но сама отправка идёт через
`broadcast_service.start_broadcast(db, bot, admin=db_user, target=..., text=...,
media_type=..., media_file_id=..., selected_buttons=..., on_progress=...)`.
`on_progress` — колбэк, которым бот правит своё сообщение с прогресс-баром;
API его не передаёт (прогресс только через `GET`). Экран «История рассылок»
в боте не меняется — читает ту же таблицу.

## Тестирование

Golden-теста на рассылку сейчас нет (в отличие от шаблонов сообщений). План
реализации должен первым шагом зафиксировать текущее поведение бота
(тексты экранов, клавиатуры, содержимое `BroadcastHistory` после отправки)
характеризационными тестами — так же, как это было сделано для уведомлений
в `tests/test_notifications_golden.py` — прежде чем выносить логику в сервис.

## Не входит в эту версию

- Загрузка медиа через API (только `file_id`).
- Персистентная очередь/возобновление рассылки после перезапуска процесса.
- Хранение выбранных кнопок в истории (не хранится и сейчас в боте).
- Расписание/отложенный старт рассылки.
